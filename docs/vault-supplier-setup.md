# Vault Supplier pairing setup

Configure `PV_WEBAUTHN_ORIGIN` with your own HTTPS management origin, for example
`https://vault.example.net`, and `PV_WEBAUTHN_RP_ID` with the matching hostname.
Use the existing immutable local Vault UUID established by application bootstrap.

Provision a persistent ECDSA P-256 PEM private signing key outside the repository,
restrict its permissions, mount it read-only into the backend, and set
`PV_VAULT_SUPPLIER_SERVER_IDENTITY_KEY_PATH` to that mounted file. Back it up securely.
No key is generated by credential issuance and no deployment-specific path is assumed.
The backend's normal controlled bootstrap creates the pairing tables additively.

After signing in, open Security and generate a pairing credential. The Supplier
client obtains the intended management origin and pinned server identity from that
credential. No client source change is required for another Vault origin.

This foundation supports pairing, installation revocation, challenge authentication,
and signed identity verification. It does not implement file reception. Its receiver
capabilities are false. An operator configuring a separate LAN listener must provide
appropriate HTTPS and host routing, limit identity/verify and installation authentication
routes to that listener, and block those LAN routes on the public proxy. Do not expose
storage, database, or administrative routes through the listener. No firewall, proxy,
certificate, mDNS, or production deployment configuration is installed by this update.

See [pairing protocol](vault-supplier-pairing-protocol-v1.md) and
[signed identity protocol](vault-supplier-lan-protocol-v1.md).
